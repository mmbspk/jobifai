# Application answers API contract

GET/PATCH `/api/settings/application-answers`: `{application_defaults,revision:string,profile_revision,sources,catalog,profile,certifications,preferences}`. Source evidence is `string[]`. PATCH `{revision,topics,import_id?}` edits supplied topic IDs only. The complete schemas are in `api/openapi.yaml`.

The ten catalog IDs are `work_rights`, `sponsorship`, `notice_period`, `earliest_start_date`, `salary`, `relocation`, `travel`, `work_arrangement`, `working_hours` and `credentials`. `additional_answers` handles candidate-authored Q&A separately. Sponsorship accepts distinct current/future object keys; its legacy boolean/null updates current sponsorship only. Search preferences appear as context and do not prove willingness for employer-specific conditions.

GET `/api/settings/application-answers/reviews?cursor=&state=active|history&limit=20`: `{items,unresolved_count,unread_count,next_cursor?}`. Review item revision is integer. Additional fields: `profile_revision:string`, `use_status:not_used|filled|replaced|submitted|submission_unknown`, `lifecycle`, `reason`, `source`. `job_id` is string, as used by bot attempt storage. GET `/reviews/{id}` includes latest 50 immutable encounters. POST `/reviews/{id}/confirm` takes `{answer,revision,profile_revision?}` and returns `{value:ApplicationDefaults,revision:string}`. POST `/reviews/read` returns 204. Reading does not resolve items.

Runtime recorder: `RecordEncounter(ctx,userID,domain.ApplicationAnswerEncounter) (reviewID,error)`, `MarkFilled(ctx,userID,encounterID,exactAnswer) error`. Caller must supply a stable non-empty encounter ID, FieldSignature or verified-equivalence GroupKey, ProfileRevision from `applicationanswers.ProfileRevision(profile)`, and `status:required|suggested`. Initial AnswerUsed must be blank. MarkFilled is idempotent only for identical actual text. Include MappingID when available for later compatible mapping confirmation. The service is independent of bot/resume and never grants provisional cache trust.

GET resume includes additive `profile_revision` body metadata and ETag. POST resume can send `If-Match` or `profile_revision`; the field is not persisted in factual profile JSON. Canonical YAML stays flat and zero model calls. Upload adds `application_answer_prefill` and the current profile revision.

Common-view response also has top-level `profile_revision`. Frontend CV save should preserve its draft but rebase this optimistic revision after a common-answer-only update, when current server CV fields match the saved CV baseline. Simply sending form.profile_revision from before the answer save will conflict; simply replacing it with any fetched revision risks clobbering concurrently changed CV fields. Keep false/null and custom-answer `employer`/`job_id` scope fields when merging/editing.

CV-origin protocol FINAL: upload returns optional `import_id` for server-retained validated clear evidence. Send that `import_id` alongside POST resume or PATCH application-answers when explicitly saving reviewed imported values. Server validates token ownership and matches exact typed topic values before attaching source=cv. Arbitrary client evidence/source flags are never accepted. Missing/wrong/expired nonempty token gets 409; changing imported values preserves manual source provenance. Tokens retain at most the last 10 imports per user and contain minimized evidence only. Canonical YAML has no token and no model call. `CaptureImport` returns `(importID,error)`, `SaveProfileWithImport(ctx,userID,profile,expectedProfileRevision,importID)` performs facts and origin attachment atomically.

Common-answer edits use a versioned topic map, preserving omitted topics and unrelated profile fields. The review inbox is separately paginated, with item and factual revisions. Reading notifications changes read state only. Candidate facts remain in the existing profile; source/review evidence lives in separate per-user records.

Pages default to 20 and cap at 50. `POST /reviews/{id}/dismiss` takes `{revision}`. Unchanged dismissed questions stay quiet; changed facts or proposals can reopen review. A control that receives newly verified replacement text keeps its original immutable answer as `use_status=replaced`; only final text can inherit a confirmed submission.

Warm derived reuse records a new immutable attempt encounter without another provider request. Unchanged known-missing facts suppress repeated model calls. Fact deferrals do not consume operational retries. Corrected safely blocked fact-deferral jobs can become eligible for normal future evaluation; active, unknown and confirmed submissions and existing review/approval queues remain held. Confirmation schedules no application.

Preparation and recovery share the current DOM-bound answer plan. Vision predictions never grant fill authority; unresolved controls remain operational selector errors. Saved factual changes and profile-load failures stop side effects rather than allowing stale facts through Submit.
